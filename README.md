# IBEX-Dashboard

Sales and financial reporting dashboard: a **Dash** (Plotly) app served by a
**Flask** server, deployed on **Vercel** with **Supabase** as the database and
login store.

Pages: Home, Sales Dashboard, Input Form (Deposit & Expense), Reports.

---

## 1. How authentication works

| Store | Purpose |
|-------|---------|
| **Supabase `app_users` table** | The **only** account store. Passwords are kept as an unsalted `sha256` hash. |
| **Supabase Auth (GoTrue)** | Optional. Used only when the typed user name is an e-mail address (`sign_in_with_password`). |

`app.py` resolves a sign-in in this order:

1. Supabase Auth, if the user name contains `@`
2. the Supabase `app_users` table

There is **no local account file**. `data/auth_users.db` was deleted from the
repository (and is now git-ignored), so the same credentials work locally and on
the deployment, and no password hashes are published.

> **Row level security is enabled** on `app_users` and `expenses`. The
> publishable/anon key (`sb_publishable_...`) reads back **zero rows** and cannot
> insert. Only the **service-role key** can read and write those tables, so it
> must be present in the running environment.

## 2. Environment variables

**Current setup:** the credentials are committed in `supabase_config.py` so the
Vercel deployment works with no dashboard configuration. That file is PUBLIC —
anyone reading the repository has the service-role key.

The recommended end state is:

1. Add the three variables in the Vercel dashboard
   (**Settings → Environment Variables**, tick Production/Preview/Development):

   | Variable | Required | Notes |
   |----------|----------|-------|
   | `SUPABASE_URL` | yes | `https://<project-ref>.supabase.co` |
   | `SUPABASE_SERVICE_ROLE_KEY` | **yes** | Supabase → Settings → API → `service_role` JWT. Required to bypass RLS. |
   | `SUPABASE_KEY` | optional | publishable/anon key, only needed for Supabase Auth sign-in |

2. Redeploy.
3. **Delete `supabase_config.py`** and rotate the service key in
   Supabase → Settings → API (a key that was public must not be reused).

`supabase_config.py` applies its values with `os.environ.setdefault`, so a local
`.env` or a value configured in the Vercel dashboard always wins over the
committed values.

For local development create `.env` in the project root with the same keys:

```dotenv
SUPABASE_URL=https://<project-ref>.supabase.co
SUPABASE_KEY=sb_publishable_...
SUPABASE_SERVICE_ROLE_KEY=<service_role JWT>
FLASK_SECRET_KEY=change-me
```

## 3. Supabase schema

```sql
create table if not exists app_users (
    id            bigint generated by default as identity primary key,
    username      text        not null unique,
    password_hash text        not null,
    created_at    timestamptz not null default now()
);

-- Keep the table private: allow no access through the anon/publishable key.
alter table app_users enable row level security;
```

The `unique` constraint on `username` is required: account creation uses an
upsert with `on_conflict=username`.

The `expenses` table and the `expense-images` storage bucket are used by the
Input Form page.

## 5. Deploy on Vercel

1. Push this repository to GitHub.
2. Import the repository in Vercel (framework preset: **Other**).
   `vercel.json` routes every request to the WSGI entry point `api/index.py`,
   which re-exports `server` from `app.py`.
3. Add the environment variables from section 2.
4. Deploy, then open `https://<your-app>.vercel.app/health`.

### Health check

`/health` reports the wiring without leaking any secret:

```json
{
  "status": "healthy",
  "serverless": true,
  "accounts_backend": "supabase",
  "supabase": {
    "url_configured": true,
    "publishable_key_configured": true,
    "service_role_key_configured": true,
    "client_configured": true,
    "publishable_key_is_denied_by_rls": false
  },
  "supabase_app_users_reachable": true,
  "supabase_error": null,
  "accounts_visible": 3,
  "data_files": { "sales_update_xlsx": true, "custom_css": true }
}
```

If `service_role_key_configured` is `false`, logins and registrations cannot
read or write `app_users` on the deployment. If `accounts_visible` is `0` while
`service_role_key_configured` is `true`, the table is empty or the key is wrong.

## 6. Troubleshooting sign-in

| Symptom | Cause | Fix |
|---------|-------|-----|
| "Invalid username or password" for a correct password | The deployment has no Supabase credentials, so only the bundled SQLite file was checked | Add `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` in Vercel and redeploy |
| Same, and the yellow hint mentions row level security | Only the publishable key is configured | Add `SUPABASE_SERVICE_ROLE_KEY` |
| "Unable to create the account." | Same two causes as above, plus a missing `unique` constraint on `username` | Follow the table definition above |
| Logged out again right after a successful sign-in | Fixed: Dash re-fires the callback when the dashboard replaces the login form, which used to press "Logout" with `n_clicks = 0` | — |
| Signed out on every page refresh | Fixed: the first callback used to overwrite `localStorage` before the saved session was read | — |

While `SHOW_AUTH_DIAGNOSTICS` (top of `app.py`) is `True`, the login screen prints
the technical reason under the error message. Set it to `False` once the
deployment is configured.

## 7. Tests

```powershell
pytest tests -q
```

`tests/test_auth_flow.py` drives the real Dash callback over HTTP and covers
login, logout, registration, the `n_clicks == 0` re-render calls and the
`localStorage` session restore. Supabase calls are monkeypatched so the tests
are offline-safe.

## 8. Notes

* `data/` now contains only `SALES UPDATE.xlsx`, which is committed so the
  read-only Vercel filesystem can still serve the spreadsheet.
* Accounts live in Supabase, so there is nothing to keep in sync and no
  credentials are stored in the repository.
* To change a password without the UI, hash the new password
  (`python -c "import hashlib;print(hashlib.sha256(b'new-password').hexdigest())"`)
  and update `app_users.password_hash` for that user in the Supabase table
  editor. Creating the account through the app's **Create Account** form is the
  easier route.
* Passwords are stored as an unsalted `sha256` hash. Anyone who can read the
  `app_users` table can test guesses offline, so keep row level security enabled
  and the `service_role` key server-side only.
